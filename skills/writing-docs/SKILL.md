# 技术写作

写出让疲惫的工程师第一次阅读就能理解的文字。应用全部四层规则。

以下三条规则优先于各层规则：

- **删掉每一个不起作用的词。** 如果删掉一个词后句子仍然成立，就删掉它。“In order to” 改成 “to”。“It is important to note that” 整句删除。
- **使用简短、日常的词。** 用 “use”，不用 “utilize”；用 “help”，不用 “facilitate”；用 “do”，不用 “perform”。长词必须凭借更准确的含义，证明它值得占用这些篇幅。
- **如果某条规则让句子变差，就换一种方式修改，或者保持原样。** 一个句子即使遵守了全部规则，只要读起来像机器写的，就仍然失败了。

代码库就是词表。使用真实的符号、文件、标志或命令名称，不要使用它们的同义词，也不要用一段描述代替名称。

不要发明术语。使用开发者平常会说的词：“移动”“删除”“只会减少的预算”，不要使用“撤离”“棘轮”或“终局”。可以使用有名称的模式，但文档必须在第一次出现时说明其含义。在回复中提出一个新的不当用词及其替换建议，作为对 [unslop](../unslop/SKILL.md) 技能中抽象隐喻规则的补充，并附上 diff。不要修改该技能。

## 变化句子的节奏

一篇文档可能遵守了每一层规则，读起来却仍然像机器写的：每个句子都被截得很短，没有任何观点，也没有具体内容。

- 有意识地混合使用长短句。短句突出一个要点。较长的句子将事实与它的条件或后果放在一起。
- 每句表达一个意思，不代表每句都要一样长。一个句子包含两个意思时，把它拆开。一个长句只表达一个意思时，保留它。
- 在文档类型允许时表达观点。解释类文档要权衡取舍，因此应说明你如何看待这些取舍，而不只是罗列优缺点。参考类文档保持客观、平实。
- 使用具体表述，不要空泛。例如，不写“schema 变更可能引发问题”，而写“重命名一列会导致构建失败”。

## 先选择文档类型（Diátaxis）

一篇文档只采用一种类型。用两个问题来选择：内容是在帮助读者行动（做事），还是理解（思考）？它服务于学习，还是工作？

- 行动 + 学习：**教程 tutorial**。
- 行动 + 工作：**操作指南 how-to**。
- 理解 + 工作：**参考 reference**。
- 理解 + 学习：**解释 explanation**。

这套判断方法既可以用于整篇文档，也可以用于一个句子。

**教程：通过实践学习。** 让学习者成功是你的责任，不是他们的责任。开头说明学习者将构建什么，不要说他们将“学到”什么。尽早、频繁地让每个步骤产生可见结果。告诉他们应该看到什么：预期输出、提示符变化或日志行。把解释压缩成一个分句，再附上链接。保持具体。用“我们”的口吻，使用指令：“首先，做 x。现在，做 y。”

**操作指南：通往目标的步骤。** 解决一个人实际遇到的问题，而不是介绍机器能够执行的一项操作。假定读者有能力完成任务，省去教学。只写行动：不跑题、不介绍背景、不为完整而追求完整。这些内容改用链接提供。允许分支和判断：“如果你想要 x，就做 y。”根据任务命名指南：写“如何校准雷达阵列”，不要写“雷达阵列校准”。

**参考：供查阅的事实。** 只做描述。不提供指令，不劝说，不表达观点。保持平实、完整、确定。直接陈述事实、选项、限制和错误，不使用犹豫措辞。让文档结构对应所描述对象的结构，使代码和文档能够配合查阅。把内容放在读者预期的位置。能从代码生成时，就从代码生成。

**解释：理解及其原因。** 聚焦一个范围明确的主题，即使脱离产品，也应能独立阅读。每个标题前面隐含加上“关于……”时，都应成立。围绕一个真实的“为什么”问题展开。提供背景，包括设计决策、历史、约束和替代方案。只有这一类文档允许表达观点。

不要混合类型：不要在教程中放参考表格，不要在参考文档中加入手把手教学，也不要在操作指南中展开论证。应当拆分，再用链接连接。

## 面向读者写句子（Google 开发者写作风格）

- 用“你”称呼读者，使用现在时。只有事情确实发生在以后时，才使用 “will”。
- 说明谁做什么：写“编译器检查”，不要写“被检查”。只有执行者未知或无关紧要时，才可以使用被动语态。
- 把指令写成命令：“点击提交。”直接陈述事实。不要写“应该被完成”。
- 条件放在指令之前：“要删除文档，请点击删除。”
- 先写常见情况，再写例外。
- 语气像一位懂行的朋友。不使用流行术语或比喻性语言，指令中不使用 “please”，操作步骤中绝不使用 “simply”“easy” 或 “quickly”。如果事情简单，读者就不会来查文档。
- 不要提前预告，例如“我们即将支持……”。不要连续用同一个短语开头。
- 链接文字应说明链接指向哪里，使用页面标题或简短描述。绝不使用“点击这里”。优先在当前页面提供一句背景说明，而不是把读者引向站外链接。
- 标题要传达要点，而不只是主题。例如，写“先选择文档类型”，不要只写“类型”。英文标题使用句首字母大写。任务标题使用直接的动词短语，例如“创建实例”；概念标题使用名词短语。每页只有一个一级标题，不跳过标题层级。
- 有顺序的内容使用编号列表，其他内容使用项目列表。用完整句子引出列表。各项保持平行结构。
- 代码相关文本使用代码字体。UI 元素使用粗体。使用序列逗号。去掉 “etc.”，在前面直接说明列表只列出部分内容。

## 一次只让读者处理一个意思（STE 规则）

- 每句只包含一条指令。其他句子每句只表达一个意思。
- 指令句超过约 20 个词时拆分，其他句子超过约 25 个词时拆分。
- 警告或条件放在它所约束的步骤之前：“如果热油接触皮肤，可能造成伤害。”
- 保留 “the” 和 “a”：“Remove backup file” 有两种解读，“Remove the backup file” 只有一种。
- 每个词只承担一个含义和一种作用，并始终保持一致。如果 “check” 表示检查，就不要同时用它表示制止。
- 每种动作选择一个词，并一直使用它。例如，使用 “start”，不要这里用 “start”，那里又用 “initiate”。
- 把操作步骤写成直接命令，绝不写成叙述或被动表达：写“安装组件”，不要写“组件必须被安装”。
- 尽可能避免使用 “-ing” 形式的词。

## 不让句子产生两种解读（Global English）

- 把 “only” 和 “not” 等词放在它们修饰的词旁边：“only fails on growth” 和 “fails only on growth” 表达的意思不同。
- 拆开长串名词：“the proto import budget check script” 改成 “the script that checks the proto-import budget”。
- 让每个 “it”“they” 和 “this” 都只有一个明确的指代对象。不确定时，重复那个名词。绝不使用 “this” 或 “which” 指代整个分句。
- 不要省略动词：“Phase 1 moves the converters and Phase 2 the runtime” 中，Phase 2 没有动词。给它补上。
- 保留体现结构的小词，例如 “Ensure that the switch is off” 中的 “that”。绝不为了减少词数而牺牲清晰度。
- 并列结构中，如果重复冠词可以避免误读，就重复冠词。当客户端和主机是两个对象时，写 “the client and the host”，不要写 “the client and host”。
- 如果一个句子可以有两种分组方式，说明 “and” 或 “or” 连接的是哪些部分。“Both...and”“either...or” 和 “if...then” 都是现成的消歧工具。
- 使用句号，不使用分号。把破折号改成另一个句子。
- 括号中的内容应是完整的语法单位，或者独立成句。绝不通过添加 “(s)” 表达复数。
- 不使用斜杠：写 “a, b, or both”，不要写 “a/b” 或 “and/or”。
- 对每个事物始终使用同一个名称。如果文档用 “the gate”“the ratchet” 和 “the budget check” 指代同一个东西，读者就会以为是三个东西。没有变化的内容不要反复改写。
- 不使用习语、口语化表达、拉丁语缩写和隐喻。

## 文风与仓库约定

- 对本技能处理的每篇文档，都阅读并应用 [unslop](../unslop/SKILL.md) 技能。AI 用词、填充语、犹豫措辞和格式特征等模式清单由该技能负责。
- PR 描述和提交信息也是写作。除 Diátaxis 外，其他各层都适用。PR 正文应是一份评审者能在一分钟内读完的简报。不要粘贴 swarm 日志、SHA 列表或指标表格。用链接提供这些内容。
- 产品 UI 字符串不属于文档。使用产品自己的文案指南。
- 代码示例使用 Tab 缩进。使用真实路径。关于数量或目录树的每项描述，在提交落地时都必须准确，并附上重新生成这些结果的命令。

## 完整改写示例

改写前：

> proto 导入棘轮预算脚本参数的配置通过 budget.json 执行。请注意，务必记住：运行 --write 会更新已提交的预算，使其反映当前计数，而这项操作只应该在降低预算时执行。如果超出，CI 失败。

改写后：

> `budget.mjs` 从 `budget.json` 读取已提交的预算，并统计导入 proto 的文件数。如果计数超过预算，CI 失败。仅在降低预算时运行 `budget.mjs --write`。
