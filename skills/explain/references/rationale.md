# 调查历史设计原因

用于“当初为什么这样做”，不用于替代运行机制追踪或当前方案评价。

## 从具体锚点调查

确认目标文件、符号、数值或设计。先看实现、注释和相邻文档，再沿已有线索查引入或实质修改它的提交、PR、设计记录和工单。仓库有 Git 历史时，可按需使用 `git blame`、`git log --follow`、`git log -S` 或 `git log -G`；不是每次全部执行。

注意最后修改不一定是最初原因，声明的常量也不一定被使用。核对该选择是否仍生效，以及相关记录是否对应目标版本。

需要扩展时，根据具体 PR、事件、作者或术语查询可用的相关来源。没有 Git、连接或权限时说明材料缺口；不默认搜索所有工具、团队聊天或整个历史。

## 让结论匹配证据

- 明确记录：作者、PR、设计记录等直接说明原因。引用具体出处，说明该记录涉及哪个选择。
- 有支持的推断：多项材料支持一种解释，但未直接记录意图。说明证据如何支持推断，保留“可能”“更像是”等限定。
- 未知或冲突：查不到就指出具体未知点；记录互相冲突时同时呈现，不为了故事顺畅选一个。

这些区别用于推理与措辞，不要求给每句话打印等级标签或固定报告。用户提出“是不是为了性能”时，将它当作待查假设；没有记录或测量不能确认。

实现显示的作用、历史选择的理由、理由现在是否成立是不同问题。需要时分开说明。当前代码能带来某种收益，不证明作者当初就以它为目标；没有找到证据，也不证明历史上没有考虑它。

## 收敛

找到足够回答目标原因的记录后停止。相关材料已查而原因仍未知时，说明查了哪些有关来源、缺什么，不用完整覆盖表或合理故事补齐。若后续要修改，提炼仍需保留的行为与约束，不擅自实施。
