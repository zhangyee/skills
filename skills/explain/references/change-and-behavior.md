# 解释变更影响与现象

## 变更说明

读取实际 diff 及前后文，确认比较的版本。用户只给假设改动时，明确这是对假设的分析，没有真实 diff 时不声称已经发生。

按触发条件说明改前与改后的行为，而不只复述增删行。追受影响的接口消费者、数据格式、状态写入、错误传播、清理时机和持久化结果；只保留有具体传播路径的影响。

调用了取消 API 不必然等于撤销已经完成的副作用，也不必然更新业务状态。类似保证要核对函数契约、调用时机与所有受影响的状态，而不是根据方法名推断。

把已确认差异、推断的风险和实际验证结果分清。解释风险不自动要求修改、运行整个应用或编写测试；若现有授权与环境允许且运行能决定结论，可选择最小的有意义验证。未经执行就说明仅做了静态分析。

## 现象与差异

先固定已知输入、版本、配置、期望与实际表现。根据观察提出能被区分的解释，沿相关分支寻找支持或反证；不要把第一个合理解释认作根因。

追请求、数据或状态时，按需读主文件指向的 trace.md。核对日志、测试、复现与实际代码是否对应同一条件。静态代码允许某条路径，不等于用户环境一定走过它；时间相近也不能单独证明因果。

说明发生条件怎样经过具体机制得到结果，以及哪些因素仍未排除。性能或可靠性结论要对应测量条件、指标和证据，不能把存在缓存或重试写成已测得收益。

## 收敛

能连接条件与结果并指出关键证据时结束。尚不能确定时，给出最影响判断的缺口和可区分假设的检查方向，不罗列无关猜测。用户只要求解释时不改文件，已明确授权修复时继续完成修复。
