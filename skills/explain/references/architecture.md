# 架构分工与当前取舍

## 解释现有结构

先说明系统或子系统解决什么问题，再查核心模块的职责、公开接口、依赖方向、组合入口及数据和状态归属。读取代表性的真实协作路径，核对结构描述。

目录和模式名称只用于导航。解释一个边界时，说明谁提供什么能力、谁消费、通过什么接口，以及失败或状态由谁承担。不要只列“控制层、服务层、数据层”。

范围随问题收敛。定位职责时可只解释相关模块；整体入门先给足够的高层结构，再展开重要或容易误解的部分。依赖关系不等于运行顺序，必要时分别表达。

## 评价当前方案

先从材料确认需求和约束，例如响应时间、结果可靠性、数据一致性、现有接口、运维能力。未给出的关键条件标为假设；有默认建议时说清其依据。

围绕会改变选择的维度比较当前方案与相关替代方案，连接到实际行为：谁需要等待、失败谁处理、状态存在哪里、需要新增什么依赖。给有条件的判断，不强凑候选数量或均衡优缺点。

区分当前结构、改造建议和历史动机。“这种分工可以隔离数据源变化”是当前评价，不自动等于“作者当初为了隔离变化而设计”。历史问题另读主文件指向的 rationale.md。

解释已有架构不会自动进入设计、骨架生成或实现。用户要求提出方案时可以建议；要求实现时继续已授权工作，不把建议误写成已完成改造。

## 输出与停止

交付足够读者定位相关职责、理解真实协作和主要限制的说明。比较用表格或文字即可，结构差异难以看清时再画图。无需生成全库地图或列出无关技术债。

结论覆盖会改变推荐的主要约束后结束。无法确定的约束说明它如何影响判断，不用通用架构口号代替答案。
